基线：`bf41409`，2026-09-22。结论：**现有 happy path 可运行，但本轮产品化验收不通过。需要修复三个可靠性/正确性问题，并重做工作台的信息架构和视觉设计。**

- 独立重跑 `pnpm test`：87 文件、612 测试通过。
- 实际 Chrome 浏览器：1440×960 桌面、390×844 手机；工作台、设置、项目、远端审批、管理后台。
- 通过真实 mock 容器完成创建任务、审批、下载内容精确核对、刷新恢复及第二轮跟进。
- 在隔离 8892 集群上额外做结果提交故障注入和节点注册乱序验证；工作台使用独立 8799 和 `data/acceptance-review`，未使用 8797/8890 用户平台或真实模型额度。
- 本次没有重跑完整集群故障矩阵、生产负载、桌面打包；不以历史报告代替本次验证。
- 仅添加验收报告和重设计说明，未修复应用实现。临时脚本、截图和 JSON 证据位于 `data/acceptance-review/`，该目录被 Git 忽略；跨机器转交需要一并附带证据。

## 功能缺陷

### F1 · P1 · 结果提交的一次临时 503 会丢失已成功执行的成果

定位：`apps/worker/src/index.ts:293`、`:301`；控制面 `apps/cloud/src/index.ts:397`。

复现：`node data/acceptance-review/finish-fault.mjs`。独立 Worker 使用真实 Docker 与 mock 模型；代理只对第一次成功结果的 `/finish` 返回一次 503，下一次请求即恢复正常。Docker socket shim 仅将固定 socket 路径映射到 macOS 当前 Docker context，不改执行逻辑。

实测：

- 正常对照：`succeeded`，成果含 `cloud-proof.txt`。
- 注入 503：Worker 已产生 `ok:true` 且包含该文件的结果；随后 catch 重新提交 `ok:false,error:"Control 503"`，最终 `failed`，成果列表为空。
- finally 强制删除执行容器；文件位于临时工作区，未得到控制面持久保存。

影响：一次短暂控制面不可用就把成功任务变成失败，丢失成果；用户按失败重试还可能重复外部副作用。

修复方向：区分执行失败与结果交付失败；对原始完成结果提供幂等提交、确认与有界重试，提交确认前保留可恢复结果。控制面终态重放应识别同一完成提交，不能仅在 Worker 上加通用重试。

验收：覆盖首次提交前 503、数据库提交成功但响应丢失、重复 finish、并发 finish/取消；状态和成果均只能落地一次。

证据：`data/acceptance-review/finish-fault.json`。

### F2 · P1 · 远端成果“文件”预览实际读取本机同名文件

定位：`apps/web/src/App.tsx:408`、`:1050`，`apps/web/src/components/RightPanel.tsx:158`、`:239`，`apps/web/src/lib/api.ts:436`。

复现：`node data/acceptance-review/artifact-preview.mjs`。

1. 远端任务生成 `cloud-proof.txt`，下载内容为 `PIG_CLOUD_CONTAINER_OK`。
2. 本机工作目录创建同名文件，内容为 `LOCAL_ONLY_REVIEW_SENTINEL`。
3. 打开远端会话，点击右侧产物，再切换“文件”。
4. 浏览器请求 `/api/workspace/file?path=cloud-proof.txt`，界面显示本机 sentinel；远端下载内容仍为 `PIG_CLOUD_CONTAINER_OK`。

影响：同一个远端产物，“对比”与“文件”可能来自不同数据源；用户会把本机文件误当成远端执行成果。没有本机同名文件时预览也不能正确读取远端产物。界面还把远端产物标为本机工作区路径。

修复方向：产物身份应包含来源、run/version 和 artifact ID；远端预览使用远端已授权的成果接口。本地落盘必须通过显式导入，正确区分本地工作区、远端工作区和历史版本。

验收：无本机文件、同名不同内容、跨两次远端运行、切换任务、导入前后均显示正确来源与内容；用户不需要通过猜测确定文件在哪。

证据：`data/acceptance-review/artifact-preview.json`、`remote-artifact-wrong-source.png`。

### F3 · P1 · 旧节点的迟到注册重试能使新代节点失效

定位：`apps/cloud/src/cluster.ts:119`，`apps/worker/src/index.ts:337`。

复现：`node data/acceptance-review/generation.mjs`。同一 workerId 的代次 A 注册 → B 注册 → 重放 A 注册 → B 心跳。

实测：A、B、迟到 A 的注册全部返回 200；B 心跳返回 409 `Worker generation expired`，A 心跳恢复 200。

触发场景：A 注册提交成功但响应丢失，A 按现有逻辑重试期间 B 已接替注册，迟到的 A 重试再次覆盖 B。当前随机 instanceId 只能表达不同身份，无法区分已被替代的代次。

影响：新的合法节点会被旧请求挤掉。根据同一注册事务的 SQL，若 B 已领取任务，还会把 B 的活动任务标记为失败；这一任务失效影响为代码推导，本次协议复现未另启动 B 的真实执行容器。

修复方向：让注册重试具有稳定幂等语义，记录被替代代次，或以服务端有序 epoch/CAS 等机制阻止旧代重新取得所有权。

验收：注册响应丢失、乱序重试、并发替换时，已失效代次不可恢复所有权，新代任务不被旧请求取消。

证据：`data/acceptance-review/generation.json`。

## UI / UX 验收：需要结构性重设计

以下是产品和设计评审结论，与功能故障分开记录，不把主观审美包装成自动测试失败。

| 编号 | 当前证据与问题 | 重设计目标 |
| --- | --- | --- |
| U1 | 1440px 桌面顶部仍两行；导航、搜索、主题、执行位置、引擎、审批、运行地址和设置挤在全局栏 | 全局导航进侧栏；任务配置归任务；桌面内容标题栏维持单行 |
| U2 | 空任务仍常驻约 300px 文件面板，内部分为两个空区；欢迎语与底部输入框之间大片无用途空白 | 新任务页以输入为中心；无产物时关闭检查面板；执行后按上下文展示结果 |
| U3 | 多数操作都是小号描边按钮，辅助文字多且弱；正文、任务状态、系统提示缺少清楚的主次关系 | 重建字号、间距、色彩、按钮和状态规范，突出当前任务与下一步动作 |
| U4 | 设置为约 864px 高的单列弹窗，混杂模型、执行引擎、连接、工作目录、技能；默认展示 `subprocess: codex exec --json`、`idle`、配置文件优先级等实现细节 | 独立分组设置；基础与高级配置分离；连接状态、适用范围、保存反馈明确 |
