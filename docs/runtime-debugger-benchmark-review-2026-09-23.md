# 固定任务基准脚本交叉审查

当前 `scripts/mock-task-bench.mjs` 与 worker 是草稿，以下问题修正前不能把生成的数字用作验收证据：

1. hot 的每个样本仍调用 oneSample 新建子进程，warmup 是另一个已退出的进程；这不构成同进程预热。冷启动在 runSample 完成后计算，包含整段任务时间，并没有包含父进程发起 spawn 至 worker ready 的真实启动过程。需要明确 ready 边界，热样本复用同一运行进程。
2. productOverhead 从 total 固定减 30ms，但读写任务调用模型不止一次，流式回复还有额外延迟。要按每样本实际累计模型等待测量；不能把分位数直接相减当成开销分位数。并行重叠阶段不能直接加减，无法分离就明确不提供该项。
3. TTFT 没有 token 时用模型服务端计时或 total 代替，这是伪造首字。应取客户端收到首个文本增量的事件，无文本的审批/取消场景填 null，并区分首个工具调用事件。
4. approvals 仅运行到首项审批暂停，没有连续批准两项及验证写入；需要真实逐项批准、核对首次审批前无写入和批准后对应文件存在。
5. reconnect 只在结束后读取一次可能为空的事件库，没有断开/续传、序号或去重断言。需要有真实事件记录并模拟携带游标续传，确认无缺漏与重复。
6. cancel 的 gate 从一开始就是 resolved，模型可能在 abort 前已经完成；需要真正阻塞到取消，验证取消终态与未写入。不能用 `pending.catch(() => undefined)` 隐藏任意失败后仍出成功样本。
7. worker 清环境变量后动态导入 config 仍可能读取仓库 dotenv；应明确禁用 dotenv（例如现有 PIG_DESKTOP=1 隔离入口），所有数据与工作区指向测试临时目录。不得连接开发者真实模型或数据。
8. 长历史输入目前含未配对的 tool 消息，mock 没校验协议；需要合法历史和模型请求结构校验。读写、错误、取消、重连每个场景都要明确断言实际结果，不只测经过多少毫秒。

至少八类任务各五个冷/热成功样本，报告失败样本、环境、原始数据、统计口径、样本量限制。样本不足就如实报告失败并修复，不应以虚假精度代替行为验证。可把连接恢复单独报告为恢复耗时；不能把本机 mock 数据推断为生产容量或宣称不存在的优化前后收益。
