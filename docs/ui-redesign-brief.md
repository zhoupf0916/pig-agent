# Pig Agent 下一轮：产品界面重设计与验收缺陷修复

下面内容可作为下一轮开发指令。

---

当前版本的 UI 未通过我的验收。我要求重做信息架构、主布局、交互流程与视觉系统。上一轮功能实现可以保留，但现有页面结构不应成为设计约束。仅改颜色、圆角、阴影、边距不能算完成。

先阅读 `docs/acceptance-review-2026-09-22.md`，查看 `data/acceptance-review/` 中的真实截图和复现证据。运行当前项目后开始实施，自行做设计决策，不停在方案阶段等待我批准。

## 产品方向

把 Pig Agent 做成精致、安静、专业的 Agent 工作台。核心体验是：选工作区 → 描述任务 → 看执行 → 处理审批 → 核验成果 → 继续任务。页面应让用户立即看懂“我在哪个任务、正在做什么、需要我做什么、结果在哪里”。

采用统一中性底色、清晰文字对比、克制的品牌强调色和细分隔线。通过排版、留白与分组建立主次。正文以 14–15px 为起点，辅助信息 12–13px，不用满屏小字换取容量。统一图标、组件高度、间距、选中态和键盘焦点。避免装饰性渐变、巨型欢迎标题、反复套卡片和无意义的数据图表。

## 必须重做的页面结构

1. 全局框架：左侧稳定导航承载工作台、项目、专家、自动化等入口，账号和设置位于底部。明确区分全局导航与当前任务列表，可用分组或可切换侧栏避免叠加两条常驻侧栏。主区顶部仅保留标题、任务状态及少量上下文操作。模型、执行位置、审批策略归到任务配置中，不在全局横条堆叠。

2. 新任务：输入框成为首屏中心，与简短引导、工作区和执行配置形成一个完整区域。提供少量确实可用的示例入口。尚无产物时不占据右侧 300px。空态、对话态、运行态分别设计，不用一个巨大空三栏布局套所有状态。

3. 执行过程：主区展示易读对话；过程以紧凑摘要显示，可展开工具细节。状态要区分排队、执行、等待审批、取消中、失败和完成。等待审批直接在当前任务中处理：展示操作对象、改动 diff 或命令、影响范围与批准/拒绝按钮。原始 JSON 放高级详情。

4. 成果：提供可展开、可调整宽度的检查面板。文件预览、diff、日志、下载和版本具备明确入口。清楚标注本机/远端及所属运行；禁止把远端成果映射为本机同名文件。没有内容时收起，宽度不足时使用抽屉。对话和成果不要求用户反复打开全局远端弹窗才能关联。

5. 设置：采用独立页面或有分组导航的大型设置界面，按模型连接、执行默认值、工作区、远端连接、外观及高级选项组织；只展示真实支持的能力。每组明确当前值、作用范围、连接状态和保存结果。技术协议、命令行参数、配置文件优先级放高级说明；不要把开发文档直接铺在普通设置表单中。处理未保存修改、验证失败、保存中、连接测试及草稿保护。

6. 管理端：与工作台共享颜色、字体、组件尺度和状态语义，同时保持独立权限。Runner 采用便于扫描的紧凑列表，支持状态筛选与详情；调度策略有清楚单位、限制和作用范围。任务列表能搜索、筛选并进入同一任务的日志和成果。仅使用真实指标，缺失指标先接通数据再展示。

7. 移动端：重新组织布局。390px 下使用紧凑顶栏和抽屉导航，默认顶栏与任务栏合计目标不超过 112px；不要把桌面按钮简单换行铺满首屏。保证输入、审批、取消、下载和设置保存都可见可用，弹窗无横向溢出。桌面 1280px/1440px 顶部标题栏目标 56–64px，不能靠缩小文字强塞按钮。

## 必须一并修复的正确性问题

- F1：完成结果回传短暂 503 导致任务被标失败且成果丢失。实现完成提交的幂等确认与可恢复交付，验证响应丢失和重复提交。
- F2：远端产物“文件”预览读取本机同名文件。按来源、run/version、artifact ID 获取正确内容，验证本地同名不同内容。
- F3：旧 Worker 迟到注册覆盖新代。实现不可被旧重试逆转的代次隔离，验证乱序注册与响应丢失。

## 实施方式

先把新布局与设计规范写入简洁设计说明，再完整实现工作台和设置作为全站样板；自行截图评审并修正后，把规范推广到其余页面。不要只做一个漂亮首页，也不要借重设计改变现有鉴权、存储边界和执行语义。

对于需要改组件结构的地方直接重构；避免在现有 CSS 尾部不断追加覆盖规则。沉淀共享 token 和基础组件，但不用为了共享样式重写整个后端或更换技术栈。

持续按“实现 → 启动 → 浏览器操作 → 截图 → 自评 → 修正 → 回归”推进。遇到审美选择由你判断；只有真正不可替代的外部条件缺失才提问。保护已有用户数据，不用真实模型额度做反复 UI 冒烟。

## 完成标准

- 工作台、任务详情、设置、远端审批与成果、管理端均完成新设计，布局和信息层级有实质变化。
- 在 1440×900、1280×800、390×844 验证浅色和已有的深色模式，不允许只看空页面。
- 用明确标记的 UI 夹具覆盖至少 15 条任务、长中文标题、长 Markdown、代码块、工具结果、失败与重试；真实集成流程仍使用真实接口和 mock 执行容器，不能用夹具伪装验证通过。
- 保存重设计前后同尺寸截图：空态、执行中、审批、完成产物、错误恢复、设置、Runner 管理。每个旧问题对应新证据；如果仍存在顶栏拥挤、无用途空面板或技术说明压过主要操作，继续迭代。
- 验证完整创建/执行/审批/取消/重试/恢复/跟进/下载链路，并确保 F1/F2/F3 的新回归失败场景已通过。
- 保留现有可用能力，不用隐藏功能或删除有效测试换取通过。构建和相关测试通过，报告未验证的边界。
- 最终交付可直接打开体验的版本、前后截图、改动说明和剩余问题。“所有测试通过”只能证明相应功能，不等于视觉验收通过；不要自行用“生产级”“高级感”“95 分”替代证据。
