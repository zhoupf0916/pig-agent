# 腾讯云单机容量与联网修复记录

## 目标与边界

评估现有 4 vCPU / 3718 MiB 主机上的控制面与 Runner 数量，区分空闲实例、API 请求吞吐和真实沙箱任务。使用独立 Compose 项目 `pig-capacity`、独立数据库与随机凭据、模拟模型，不修改线上账号或执行配额，不对公网入口做绕过限流的压测。线上 1 控制面 / 2 Runner 保持运行。

安全停止条件：主机可用内存低于 700 MiB，或线上本机健康请求失败。测试不以压垮线上为目标，因此只能给出已验证的负载区间，不能宣称测到了物理极限或生产容量。

## 可复现方法

在已具有本项目镜像的授权 Linux Docker 主机、仓库根目录执行：

```bash
node scripts/benchmark-capacity.mjs
node scripts/verify-capacity-failover.mjs
```

前者测试 1/2、2/4、4/8 个控制面/Runner，任务每 Runner 单槽。每组 API 并发为 1、16、64、128，每级 10 秒；随后 24 个真实原生沙箱任务，以 9 个并发提交循环进行文件写入、读回和成果检查。模型是模拟模型，包含固定等待和 SSE 输出；API 为携带认证的任务列表读取，并非健康接口。

测试容器限额：控制面 256 MiB / 0.75 CPU；Runner 384 MiB / 0.5 CPU；数据库 256 MiB / 1 CPU；网关 192 MiB / 0.5 CPU。仅用于轻量测试，不适合依赖安装或大型构建。各阶段任务数据逐渐增加；测试负载生成器也在同一台主机上，数据库与 CPU 共享。这些条件限制了吞吐数字的外推。

脚本自动停止测试容器，保留独立测试数据库卷和 `data/capacity-review/report.json`；故障测试结果写入 `failover.json`。这些文件不含令牌，原始凭据仅保存在权限 0600 的 stack.env。意外中断后可执行：

```bash
docker compose --env-file data/capacity-review/stack.env \
  -f data/capacity-review/compose.json down
```

## 联网与回复语言

线上网关原先继承本机开发环境的 `NETWORK_DNS_MODE=public`，固定访问 Cloudflare DoH。腾讯云主机上该 HTTPS 请求实际超时；系统 DNS 解析 `www.baidu.com` 得到公网地址，HTTPS 访问返回 200。因此腾讯云 overlay 明确使用 system DNS，依然对地址执行公网校验并将 TLS 连接固定到已验证 IPv4，不回退到私网、不关闭证书验证、不开放 shell 联网。

Agent 现在被明确要求需要网页时直接调用 http_fetch 并等待一次性审批，而不是先尝试 shell 网络再误报“不支持联网”。默认用简体中文解释计划、进度、审批和结果，用户指定其他语言时遵从；代码、命令、路径、原始日志保持原文。

网络能力仍是批准单个公网 HTTPS GET。curl、npm、pip 等任意进程联网不在这次授权范围；目标站点在当前地域不可达时仍可能失败。重定向和重试需要重新审批。

验证：新增模型请求语言规则测试先失败，修复后相关 27 项测试通过；完整回归 144 文件 / 832 测试通过；cloud:build（含架构及类型检查）通过。

## 本机实测结果

| 控制面 / Runner | 任务吞吐（个/分钟） | 任务端到端 P95（含排队） | API 128 并发 RPS | API P95 |
| --- | ---: | ---: | ---: | ---: |
| 1 / 2 | 37.9 | 15.33 s | 1332 | 169 ms |
| 2 / 4 | 71.1 | 9.31 s | 1444 | 175 ms |
| 4 / 8 | 122.3 | 5.26 s | 1273 | 233 ms |

72 个任务全部成功并产生 cloud-proof.txt，8 Runner 组确实由 8 个不同节点处理任务。全部 API 样本返回 200。可用内存最低 1332 MiB，线上本机健康检查最大 34 ms、无失败。每档只有 24 个任务、API 每级 10 秒，不是长时间 soak test；未测大量历史数据、数千 SSE 长连接、真实模型限流、重型构建或公网 WAN 延迟。

故障测试：2 控制面上 12 次相同幂等键的并发提交只创建一个任务；SIGKILL 一个控制面后，在途任务通过存活实例审批并完成；SIGKILL Runner 后，租约过期的任务进入 failed，不自动重放；存活 Runner 可以处理新任务；取消后旧审批返回 409；最终新任务成功完成。执行语义是可能中途失败、需核对副作用后重试，不承诺 exactly-once。

### 配置建议

- 本机日常使用 1 个控制面即可；需要实例级故障切换时用 2 个，并配健康感知负载均衡。4 个没有带来读取吞吐增长，P95 反而上升。共享 CPU、数据库和负载生成器可能共同限制吞吐，尚未做 profiler 归因。
- 通用任务继续维持 2 个单槽 Runner；限定轻量任务后可采用 4 个。8 个已通过受限轻量测试，不能承诺 8 个任意代码任务同时执行。
- 线上每 Runner 768 MiB 上限，4 个就达 3 GiB，另有控制面、数据库、网关和系统开销，不能按空闲占用直接扩成 8 个。内存上限不是预留，也不保证所有任务同时达到上限时仍安全。
- 扩展应优先把 Runner 放到独立主机。单机多副本无法抵御主机、磁盘或数据库故障；数据库与模型网关也需独立验证容量和恢复。
- 公网入口继续遵守每 IP 10 次/秒与连接限额。内网 API 数字不代表公网单用户可发送同等频率，更不代表在线人数。

原始报告：本机及服务器的 data/capacity-review/report.json、failover.json（不入 Git）。测试容器已停止，线上实例数量和任务并发保持原值。

### 大网页导致重复审批的附加缺陷

在真实腾讯首页验收中，第一次 GET 已返回 200 和网页标题，但响应较大，旧的 trimHistory 将整组工具调用及其结果移出模型上下文，模型再次申请读取同一页面。验收脚本拒绝第二次自动批准并取消该测试任务，没有把重复申请当作成功。

增加失败行为测试：20 万字符网页结果必须在下一次模型请求里保留调用配对、标题、尾部与截断说明，原始任务记录仍完整。修复先限制单条工具结果的模型副本，再进行历史裁剪：保留前 12000 / 后 4000 字符，中间明确标注省略。完整输出和实际工具执行次数不变。此策略避免单个超大响应抹掉最近一次工具结果，不代替完整网页检索或浏览器渲染。
